# Уведомления и вопросы из существующей сессии

Это режим для обычной работающей сессии MiMo Code или Codex. Через Telegram
передаются только явные MCP-вызовы. Переписка, рассуждения и вызовы других
инструментов автоматически не пересылаются. Подключение создаёт тему бота;
отдельный агент или новая рабочая сессия не запускаются.

## Начало работы

Сервер `telegram_notify` уже добавлен в глобальные конфиги:

- MiMo: `~/.config/mimocode/mimocode.jsonc`.
- Codex CLI: `~/.codex/config.toml`.

Skill установлен в `~/.agents/skills/telegram-notify/SKILL.md`.
Если приложение было открыто до установки, перезапустите его и возобновите
нужную существующую сессию, чтобы загрузить новый MCP.

Напишите агенту, например:

> Используй skill telegram-notify. Подключи текущую сессию к Telegram,
> назови тему «Работа над API». Присылай только завершение крупных этапов,
> серьёзные препятствия и изменения плана. Вопросы задавай через Telegram
> и жди моего ответа через MCP. Между этапами проверяй входящие команды.

Агент вызывает `telegram_connect`, запоминает `binding_id` и использует
его только для этой беседы. Название темы: `MiMo · Работа над API` или
`Codex · Работа над API`. Когда доступен настоящий native session ID,
используется он; иначе агент создаёт уникальный UUID и сохраняет его
в контексте/заметках этой беседы. Независимые сессии не должны делить ID.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `telegram_connect` | Привязать существующую беседу к отдельной теме |
| `telegram_notify` | Отправить выбранное обновление |
| `telegram_send_photo` / `telegram_send_file` | Отправить вложение из рабочей папки |
| `telegram_ask` | Отправить вопрос один раз и ждать ответ |
| `telegram_wait_reply` | Продолжить ожидание без повторной отправки вопроса |
| `telegram_cancel_question` | Закрыть вопрос, отменённый или отвеченный в основном интерфейсе |
| `telegram_receive` | Получить новые сообщения/команды с сохранённого курсора |

Один вызов ожидания длится до 45 секунд, а таймаут инструмента у Codex
настроен на 90 секунд. Если ответ ещё не пришёл, агент снова вызывает
`telegram_wait_reply`. Отсутствие ответа не считается согласием или выбором
варианта по умолчанию. У каждого вопроса свой `request_id`: повтор с тем же
ID не отправляет вопрос ещё раз. Одновременно ожидается один вопрос на тему;
связанные вопросы можно отправлять одним сообщением.

Можно отвечать обычным текстом в теме или использовать Reply к вопросу.
Когда MCP забирает сообщение, бот пишет `✓ Передано через MCP` в этой теме.
Это явное подтверждение выдачи сообщения MCP-клиенту; оно не означает,
что агент уже выполнил команду.

Команды, присланные во время работы без активного вопроса, попадают в
почтовый ящик сессии. Агент проверяет его между этапами и сохраняет
`next_after_id`, чтобы не выполнять одно сообщение дважды. MCP не будит
простаивающую сессию. Для ожидания следующих задач агент может продолжать
короткие блокирующие `telegram_receive` по явной просьбе пользователя.
Периодичность уведомлений контролирует работающий агент; отдельного таймера,
исполняющего модель после остановки сессии, этот режим не добавляет.

## Хранение и ограничения

- Единственный Telegram poller остаётся в `acpbot.service`.
- Токен хранится у worker; MCP запускается через
  `~/.local/bin/telegram-notify-mcp` и использует приватный Unix socket.
- Привязки, ответы и входящие сохраняются в `~/.local/share/acpbot/store.json`.
- Поддерживается только ранее привязанный Telegram-владелец.
- Вложения для отправки должны находиться внутри зарегистрированного workspace,
  включая проверку реального пути симлинков. Фото до 10 MiB, документы до 50 MiB.
- Входящие вложения сохраняются в `.acpbot-inbox/` рабочего каталога;
  в inbox возвращаются пути к ним. Этот каталог следует исключать из Git.
- Хранятся последние 1000 сообщений на сессию и 100 вопросов. Устаревший
  курсор явно возвращает `history_truncated`; агент не должен угадывать
  отсутствующие инструкции.

## Проверка установки

Проверено через стандартный stdio MCP, без запуска новых агентов мостом:
создание темы, уведомление, фото, файл, вопрос и получение реальных ответов
`TG_OK` и `TG_OK_2`. Второй ответ вернулся из блокирующего вызова ожидания.
Обычные MiMo/Codex процессы загрузили глобальный MCP и самостоятельно
выполнили `telegram_connect` и `telegram_notify`.

37 целевых тестов проходят: в том числе изоляция сессий, авторизация,
повторная доставка, курсоры, повтор вопроса, сохранение ответа, отмена,
ограничение путей и отсутствие запуска агента при сообщении в внешнюю тему.
Сборка проходит. Полная проверка типов имеет прежние upstream-ошибки;
сравнение с исходной ревизией не выявило новых диагностик.

Исходный режим, в котором бот создаёт собственные агентские сессии,
по-прежнему существует отдельно. Для выборочных уведомлений используйте
инструменты `telegram_notify` и skill `telegram-notify`, а не `/new`.
